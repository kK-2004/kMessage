## Why

多个内部服务需要向 Telegram、飞书和钉钉发送通知，但各自直接集成渠道 API 会重复处理鉴权、格式差异、失败重试和运行状态。建设统一消息平台可以为调用方提供稳定入口，并为后续接入邮箱等渠道保留清晰扩展点。

## What Changes

- 提供面向内部服务的统一消息发送 API，支持选择渠道、目标、消息内容和调用方幂等键。
- 首期实现 Telegram、飞书和钉钉消息适配器，支持统一文本消息模型及渠道特定扩展参数。
- 提供渠道实例配置能力，使不同服务或环境可以使用独立的机器人或应用凭据。
- 异步执行消息投递，记录投递状态，并对可重试失败执行有界重试。
- 提供消息状态查询与基础运行指标，便于调用方和运维人员排查失败。
- 定义通用渠道适配器接口并预留邮箱渠道类型，但首期不实现邮箱配置和实际发送。
- 提供基于 Session 登录的网页管理后台，用于管理应用凭据、渠道实例和授权，不使用 `admin-key`。
- 提供独立 Java SDK，业务项目通过 `appKey`、`appSecret` 和消息字段调用平台 HTTP API。

## Capabilities

### New Capabilities

- `message-submission`: 统一消息发送 API、请求校验、调用方鉴权、幂等处理和状态查询。
- `channel-configuration`: Telegram、飞书、钉钉渠道实例配置、凭据引用和邮箱扩展占位。
- `message-delivery`: 异步投递、渠道适配、状态流转、失败重试及投递可观测性。

### Modified Capabilities

无。

## Impact

- 新增消息平台服务、持久化存储和后台投递工作进程。
- 新增基于 Spring Boot 3.5.6+、JDK 17+ 的服务端 Maven 应用和独立 Java SDK，并依赖 `com.kK-2004:kk-common:0.1.2`。
- 新增供内部服务调用的 HTTP API，以及 Telegram、飞书、钉钉外部 API 集成。
- 需要安全管理渠道凭据与调用方凭据，并建立日志、指标和告警。
- 调用方将依赖统一消息请求与状态模型；未来邮箱实现应遵循相同渠道适配器契约。
