## Context

当前仓库没有既有应用代码。新平台确定采用 Spring Boot 3.5.6+、JDK 17+ 的服务端 Maven 应用，并接入 `com.kK-2004:kk-common:0.1.2`；另提供不依赖 Spring 的独立 Java SDK artifact。平台需要为多个内部服务提供统一的消息发送入口，首期对接 Telegram、飞书和钉钉，并确保渠道暂时不可用时消息不会立即丢失。渠道凭据和目标格式各不相同，且未来需要在不改变调用方契约的前提下增加邮箱等渠道。

## Goals / Non-Goals

**Goals:**

- 提供稳定、可鉴权、可幂等的统一 HTTP API。
- 通过异步投递隔离调用方与外部渠道延迟和故障。
- 用统一适配器契约实现 Telegram、飞书和钉钉，并为邮箱预留接口。
- 保存完整状态流转和失败原因，支持查询、指标和告警。
- 以低运维复杂度完成首期交付，同时保留横向扩展路径。

**Non-Goals:**

- 首期不实现邮箱发送、邮件模板或 SMTP 配置。
- 首期管理后台只面向平台管理员，不提供终端用户自助控制台。
- 首期不支持营销群发、订阅管理、定时发送或复杂工作流编排。
- 不承诺所有渠道的富文本、卡片和附件能力完全一致。

## Decisions

### 采用 Spring Boot 单模块 Maven 应用并复用 kk-common

应用采用 Spring Boot 3.5.6+ 和 JDK 17+，源码统一放在 `com.kk2004.kmessage.*`，构建为一个 Maven 模块。通过 GitHub Packages 引入 `com.kK-2004:kk-common:0.1.2`，复用 `TransDTO`、统一异常体系、全局异常处理和 `RequestContext`，并使用其 traceId 异步透传能力关联 API 与 worker 日志。

`kk-common` 的 web 和 exception 自动装配保持启用。首期可靠队列基于关系型数据库，因此 Redis 和 Redisson 自动装配显式关闭；任务领取和并发控制使用数据库事务及行锁，不依赖分布式锁。相比复制公共基础代码，这能保持跨服务行为一致；相比全面启用公共包所有能力，该选择避免无需求的 Redis 连接和运行依赖。

### 管理后台使用 Session，业务调用使用 appKey/appSecret

删除 bootstrap `admin-key` 和管理 API header 鉴权。管理员通过网页登录表单建立 HttpOnly Session，管理页面和 `/api/admin/**` API 均校验 Session。初始管理员账号密码由部署环境变量提供，不写入页面、日志或响应。

每个业务应用拥有公开标识 `appKey` 和只展示一次的 `appSecret`。服务端仅保存 `appSecret` 哈希；业务 HTTP 请求通过 `X-App-Key` 和 `X-App-Secret` 鉴权。轮换 secret 后旧 secret 立即失效。

### 提供独立 Java SDK

SDK 使用 JDK `HttpClient` 和 Jackson，将 `appKey`、`appSecret`、渠道实例、目标、正文、幂等键和扩展参数转换为 HTTP 请求。SDK 不包含管理能力，也不依赖服务端 Spring Boot artifact。

### 采用模块化单体并分离 API 与 worker 运行角色

首期应用按提交、配置、投递和渠道适配器划分模块，同一代码库可启动 API 角色和一个或多个 worker 角色。相比一开始拆分微服务，该方案减少部署、契约协调和故障排查成本；模块边界与持久化任务契约允许后续独立拆分投递服务。

### 使用持久化任务表作为首期可靠队列

API 在同一数据库事务中写入消息记录和待投递任务，然后返回 `202 Accepted`。worker 通过可竞争锁定的批量领取机制处理任务。相比首期引入外部消息队列，此方案部署更简单并避免数据库与队列双写一致性问题；当吞吐量超出数据库队列能力时，可在保持消息状态模型不变的情况下替换为专用队列。

消息状态使用 `accepted -> delivering -> delivered` 成功路径，以及 `accepted/delivering -> retrying -> failed` 失败路径。每次尝试单独记录渠道响应摘要、错误分类和时间。

### 使用统一消息信封和渠道适配器契约

统一消息信封包含调用方、渠道实例、目标、文本内容、幂等键和可选渠道扩展参数。适配器实现统一的 `send` 契约，并将外部响应归一化为成功、可重试失败或永久失败。

首期实现 `telegram`、`feishu` 和 `dingtalk` 适配器。注册 `email` 渠道类型和适配器接口定义，但不提供可启用的邮箱实例或发送实现。相比为每个渠道暴露独立 API，该方式可保持调用方集成稳定；代价是渠道特有功能必须放在明确隔离的扩展参数中。

### 渠道实例与目标分离

渠道实例描述发送身份及凭据引用，例如 Telegram bot 或飞书/钉钉机器人；每次发送请求提供目标标识。调用方只可使用被授权的渠道实例。凭据不直接出现在发送请求、普通查询响应或日志中，并通过部署环境支持的 secret provider 或加密存储读取。

### appKey/appSecret 鉴权、授权范围和幂等

内部调用方使用可轮换 appKey/appSecret 鉴权，服务端仅保存 appSecret 安全哈希。每个调用方配置允许使用的渠道实例和请求速率限制。调用方必须提供幂等键；在同一调用方作用域内，重复键返回原消息，不重复创建投递任务。若相同键对应不同请求载荷，返回冲突错误。

### 有界重试和错误分类

适配器必须将超时、限流和渠道服务端错误分类为可重试失败，将无效目标、认证失败和不支持的消息分类为永久失败。可重试失败使用带抖动的指数退避，并受最大尝试次数和最大投递时间限制。耗尽重试后消息进入 `failed`，由指标和告警暴露，不自动无限重放。

### 可观测性不泄露敏感内容

结构化日志、指标和追踪使用消息 ID、调用方、渠道类型、渠道实例 ID、状态和错误分类关联。默认不记录凭据、完整消息正文或渠道原始响应；诊断字段必须经过脱敏和长度限制。

## Risks / Trade-offs

- [数据库任务表在高吞吐下可能成为瓶颈] → 使用批量领取、索引、短事务和横向 worker；达到约定容量阈值后迁移到专用队列。
- [外部渠道语义和限流规则不同] → 由适配器执行错误分类，并按渠道实例隔离并发和速率限制。
- [渠道扩展参数削弱统一模型] → 核心文本消息保持跨渠道一致，对扩展参数按渠道进行严格 schema 校验。
- [凭据泄露会导致外部渠道被滥用] → 凭据引用与业务数据分离，响应和日志脱敏，限制管理权限并支持轮换。
- [异步返回意味着调用方不能立即确认送达] → 明确返回 `accepted` 状态，提供状态查询和失败告警。
- [私有 GitHub Packages 依赖可能阻塞构建和部署] → 为本地、CI 和部署环境提供最小 `read:packages` Maven 凭据配置，并在构建早期验证依赖解析。

## Migration Plan

1. 建立数据库 schema、API 鉴权和渠道配置管理能力，但暂不允许业务流量。
2. 配置测试渠道实例，验证三个适配器、错误分类和重试行为。
3. 启动 worker 和监控，通过管理后台向少量调用方发放受限 appKey/appSecret 并逐步放量。
4. 验证成功率、延迟、重试积压和限流后扩大调用范围。
5. 回滚时停止接收新请求并保留消息与尝试记录；修复后可继续处理未完成任务。
